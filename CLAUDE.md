# CLAUDE.md — coding conventions for AI assistants

This file is read by AI coding assistants (Claude Code, Cursor, GitHub
Copilot Workspace, etc.) before they touch this repo. Humans should also
read it; it's the canonical style guide.

## TL;DR

1. **Java only.** No Kotlin, no Groovy in app code. Build files (Gradle)
   stay in Groovy DSL for the moment.
2. **`:core` is Android-free.** Anything that imports `android.*` belongs
   in `:app`.
3. **Every CI step is a Gradle task.** Workflow YAML calls `./gradlew
   <task>`. Never sneak `run: bash …` glue into the workflow.
4. **Tests come with the code.** PRs that drop coverage below 95% line /
   90% branch (or 100% line in `:core`) won't merge — JaCoCo enforces it.
5. **Don't add dependencies on a whim.** `:core` has zero runtime deps;
   keep it that way. `:app` should think twice before adding any new
   library.

## Module rules

### `:core`

- Plain `java-library` Gradle plugin. **Source compatibility: 17.**
- **Zero runtime dependencies.** Use `java.net.http`, `java.util.Base64`,
  the bundled `Json` helper, etc. If you need real JSON parsing, talk
  about it in a PR before adding Jackson/Gson/Moshi.
- Public API lives in `com.transcription.core`. No internal sub-packages.
- Test deps allowed: JUnit 4, Mockito, OkHttp's MockWebServer.
- The audio fixture at `core/src/test/resources/fixtures/sample-whatsapp-ptt.opus`
  is a real WhatsApp PTT file. Use it to validate any new code path that
  touches audio bytes.

### `:app`

- `com.android.application` Gradle plugin. `compileSdk 34`, `minSdk 24`.
- One activity (`MainActivity`) for the share target + result, one
  activity (`SettingsActivity`) for preferences. Don't add navigation
  graphs, fragments, or DI frameworks until there's a second screen that
  justifies them.
- Threading: `ExecutorService` + `Handler(Looper.getMainLooper())`. No
  RxJava, no coroutines (we're in Java), no `AsyncTask`. If we need
  cancellation we'll move to `WorkManager` — until then, keep it boring.
- Tests run on the JVM via Robolectric. No instrumented Espresso tests
  in CI yet; if you need one, gate it behind a separate workflow.

## Code style

- 4-space indentation. Lines wrap at ~100 columns.
- One top-level class per file. Filenames match the class name.
- `final` fields by default; mutable state needs justification.
- `@Nullable` / `@NonNull` from `androidx.annotation` on `:app`. `:core`
  uses plain documentation (no annotation deps).
- Prefer `Objects.requireNonNull` at the start of constructors and
  public methods. Validate inputs at the boundary; trust them inside.
- **Don't write comments that restate the code.** Comment the *why* —
  hidden invariants, surprising trade-offs, "this looks redundant but
  removing it broke X". Method names and small methods do the rest.
- Javadoc: required on every `public` class/method in `:core`. Optional
  in `:app` (the package is small and the names are self-explanatory).

## Tests

- JUnit 4. **No JUnit 5 yet** — Robolectric and AGP integrate more
  cleanly with JUnit 4 in this project.
- Test names: `methodUnderTest_condition_expectedOutcome`. Failures
  should make the cause obvious without reading the test body.
- Use `assertThrows` (JUnit 4.13+) for exception expectations. Don't use
  `@Test(expected=…)` — it can't assert the message.
- For HTTP: MockWebServer in `:core`, never a real network. For
  Robolectric: `ShadowContentResolver.registerInputStream` is your
  friend.
- Add at least one failing test before writing the fix. The CI history
  should show a red commit followed by a green one.

## Commits and PRs

- Conventional-ish messages: `feat:`, `fix:`, `chore:`, `docs:`, `test:`.
- Imperative mood. ≤72 char subject. Body explains *why*, not *what*.
- One logical change per commit. Squash-merge is fine for trivial PRs;
  keep history readable for substantive ones.
- Do **not** include "Generated by ..." or AI-attribution lines unless
  the maintainer explicitly asks. Credit goes in the PR description.

## Things AI assistants get wrong here

These are the patterns we *don't* want, listed so future agents (and
humans) can recognize the smell:

- ❌ Adding a Kotlin file "because it's shorter". This codebase is Java.
- ❌ Pulling in OkHttp / Retrofit / Gson into `:core`. Use
  {@code HttpURLConnection}.
- ❌ **Using `java.net.http.HttpClient` anywhere that ships in the APK.**
  It's a JDK 11+ class that is **not** in the Android runtime. Tests
  pass on the JVM and the app crashes on the device with
  `NoClassDefFoundError`. `:core` is therefore restricted to the
  Android-compatible `java.net.*` API.
- ❌ Inlining shell scripts in the GitHub Actions YAML instead of a
  Gradle task.
- ❌ Skipping a test because "it's hard to mock". If it's hard to mock,
  the design is wrong — refactor the production code.
- ❌ Wrapping every `IOException` in a runtime exception "for
  convenience". The engine API distinguishes I/O failure from server
  error on purpose.
- ❌ Adding a `@SuppressWarnings("all")`. If the warning is real, fix
  it. If it's noise, suppress *that one warning* with a comment.
- ❌ Writing a "TODO: add tests later" comment. Tests come with the code.
- ❌ Catch-and-rethrow with no value-add (no extra context, no
  type change). Just let the exception propagate.

## When in doubt

Open a draft PR with the question in the description. The maintainer
would much rather discuss an approach in 50 lines of code than receive
a 500-line refactor that took the project the wrong direction.
